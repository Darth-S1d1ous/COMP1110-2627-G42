## 1. Purpose and research questions

We evaluate whether coordinating **dependence among drivers' route recommendations**, while preserving each driver's conditional full-path marginal distribution, reduces sustained network overload. We also test the limits imposed by delayed/partial traffic observations and imperfect driver compliance. **[Proposal §§1.2–1.3, 3.1, 3.3]**

- **RQ1 — Value of coordination:** Does feedback-driven coordination reduce the discounted overload score relative to independently sampled recommendations?
- **RQ2 — Value of feedback:** Does adaptive coordination outperform fixed or feedback-independent random coordination when all use the same individual navigation policies?
- **RQ3 — Robustness:** How do recommendation acceptance (compliance), observation delay, and partial observation affect the benefit?
- **RQ4 — Distributional cost:** Are network improvements accompanied by higher travel time for particular drivers, especially those in the upper tail of extra travel time?
- **Validity gate — Marginals:** Do all implemented coordination samplers preserve each driver's *conditional full-path* route recommendation distribution? This is a feasibility constraint, not a performance goal.

## 2. Methods and baselines

All methods receive navigation marginals `p_{i,t}` generated by **the same frozen individual navigation policies**. The policy inputs may evolve differently across simulation runs because actions alter future traffic. The coordinator has access only to permitted observations and marginal probabilities at each decision epoch, not simulator ground truth. **[Proposal §3.1]**

| ID | Method | Joint recommendation rule | Role |
|---|---|---|---|
| IND | Independent | Draw each driver's recommended path independently from `p_{i,t}`. | Main baseline **[Proposal]** |
| FIX | Fixed coordination | Use a valid marginal-preserving joint sampler with coupling parameters fixed across decision epochs, independent of feedback. | Static coordination baseline **[Proposal]** |
| RND | Random coordination | Draw valid coupling parameters from a pre-specified distribution independently of current feedback, then sample valid joint recommendations. | Non-adaptive coordination baseline **[Proposal]** |
| ADP | Adaptive / learned coordination | Choose valid coupling parameters as a function of permitted delayed/partial observations and current navigation marginals; sample from the corresponding valid joint distribution. | Candidate proposed method **[Proposal]** |

**Implementation note:** The proposal identifies Gaussian-copula sampling as a practical tunable sampler, dependent rounding as a marginal-preserving comparison, direct feedback-rule search and model-predictive coordination as candidate adaptive approaches, and regional multi-agent learning as optional. **[Proposal §§3.2, 4.1–4.2]** We do **not** assume that all adaptive frameworks will be delivered: the final report must name the one(s) actually implemented. Dependent rounding can be included as a supplementary method (`DR`) if delivered; it is not the same axis as the four policy types above.

**Baseline parameter policy [Proposed]:** Specify and freeze the FIX coupling parameter and the RND parameter distribution **before held-out evaluation**. Any tuning must use training/validation scenarios only; do not select the best fixed configuration after looking at test outcomes.

## 3. Experimental environments

| Stage | Environment | Purpose | Status |
|---|---|---|---|
| A | Small constructed road network with converging routes / bottleneck | Debug conservation of marginals; demonstrate why route dispersion may or may not imply arrival dispersion; obtain interpretable traces. | Core **[Proposal]** |
| B | MoST Monaco traffic network in SUMO + TraCI | Test whether effects remain under a realistic road topology and traffic evolution. | Core target **[Proposal]** |
| B fallback | Medium synthetic grid if MoST/TraCI setup proves impractical | Preserve a valid, reproducible simulation comparison. | Explicit fallback **[Proposal]** |

At a minimum, each scenario must define: road graph; monitored links; per-link occupancy thresholds; vehicle origins, destinations and departure times; available full paths; frozen navigation policies; decision interval; observation coverage and delay; driver compliance process; simulation step duration; and a reproducible termination rule for the post-event dispersal episode.

**Important:** The simulator's true state is used to calculate scores **after the decision**. The coordinator may use only its restricted, delayed observations; no future link occupancy, other unobserved true states, or realized future compliance is allowed as an input. **[Proposal §3.1]**

## 4. Experiment matrix

### E0 — Sanity checks (run before comparing J)

**Goal:** Confirm the system is evaluating the intended policy family, rather than measuring a programming artifact.

1. For the same decision inputs, repeatedly sample recommendations from every sampler and check empirical driver-level marginals against `p_{i,t}`; where an exact joint representation is available, check equality analytically/numerically as well.
2. Verify all proposed paths are valid full origin–destination routes and that already-traversed prefixes are respected.
3. Verify the coordinator does not receive full simulator ground truth when observations are delayed or partial.
4. Use hand-calculated toy overload traces to unit-test `J_0.90` and `J_0.99`; check that empty overload gives `J=0`.
5. Test that matched demand and initial states are reproduced across methods, and that the episode termination rule is consistent.

**Pass criterion [Proposed]:** No invalid paths or information leaks; the theoretical marginal-preservation property is verified where possible and finite-sample marginal deviations fall within pre-agreed Monte Carlo uncertainty. Do not demand exactly zero *empirical* error after a finite number of samples.

### E1 — Main comparison: is coordination useful?

**Question:** Under a fixed traffic scenario, does ADP improve overload relative to IND, FIX and RND?

- Environment: Stage A first; repeat on Stage B if feasible.
- Methods: `IND`, `FIX`, `RND`, `ADP` (any additional delivered baseline in a separate clearly labelled row).
- Conditions: one *predeclared* reference compliance setting, observation coverage setting and delay setting **representative of the project's delayed/partial-feedback question**. Add a fully observed / zero-delay setting only as an idealized control, not as a replacement for the main setting.
- Recommended preliminary repetitions: **10 matched seeds per configuration**; **[Proposed]** raise to 20–30 if runtime permits and uncertainty is too large.
- Primary endpoint: episode `J_0.90` (lower is better).
- Secondary endpoints: `J_0.99`; mean/median/upper-tail per-driver extra travel time versus IND; validity of marginal preservation.

**Interpretation:** Compare ADP–IND to estimate the value of adaptive coordination; compare ADP–FIX and ADP–RND to isolate the additional value of feedback over non-adaptive dependence control. A comparison at a single setting does **not** establish robustness.

### E2 — Driver compliance sensitivity

**Question:** Does coordination retain its benefit when some drivers reject the recommendation?

- Vary the probability of accepting a recommendation. **[Proposed illustrative levels]** `{1.0, 0.8, 0.6, 0.4}`.
- Hold the network, demand design, observation setting, navigation policy and evaluation definition fixed at the E1 reference setting.
- Run every comparison method at every compliance level using matched seeds.
- Start with fixed-probability acceptance. If delivered, add a **separate**, explicitly described state-dependent acceptance experiment; do not mix the two models in the same line without labels.
- Report the paired absolute difference in `J_0.90` and relative improvement over IND, with uncertainty, as compliance changes.

**Important:** Noncompliance affects **realized paths**, not whether the *recommendation sampler* preserves marginals. Assess those properties separately.

### E3 — Observation delay / partial-feedback sensitivity

**Question:** Can adaptation help when the coordinator sees old or incomplete traffic data?

- **[Proposed illustrative delays]** `{0, 30, 60, 120}` seconds; use only delays compatible with your simulation/decision interval and explicitly define rounding or history lookup.
- Hold the compliance model and other variables fixed at the E1 reference values.
- Run all methods for each delay with matched seeds. If a baseline is independent of feedback, its *coordinator* should not change with delay, but its frozen **individual** navigation policy may still use delayed inputs; record these choices carefully.
- **Partial observation [Proposed, optional core robustness check]:** Run at least one predetermined subset of monitored links visible to the coordinator versus full observation. Do not select visible links based on held-out outcomes.
- Do not unintentionally give ADP accurate instantaneous data while imposing delay on other methods.

### E4 — Travel-time distribution / fairness (analysis of E1–E3 runs)

This is primarily an **analysis**, not a separate large simulation sweep. Use matched vehicles/OD requests and the Task 1 definition of `ΔTT_i = TT_i^method − TT_i^IND`, measured against the paired IND run. Report distribution summaries, e.g. mean, median, 90th/95th percentile and proportion with positive extra travel time **[Proposed summaries]**. Show whether reduction in overload is purchased by concentrated losses for a minority of drivers. **[Proposal §4.4]**

### E5 — Optional extensions (only after the core evaluation works)

- State-dependent compliance model; increased number of jointly coordinated drivers; ablations of sampler parameters; dependent-rounding comparison; regional multi-agent coordination or more extensive horizon search. **[Proposal §4.2]**
- Report these as extensions, not prerequisites for completing the core study.

## 5. Controlled conditions and reproducibility

**Matched comparisons [Proposal §3.3; implementation details proposed]:**

| Hold fixed or pre-generate | Rationale |
|---|---|
| Network topology, monitored links and `C_e` thresholds | Prevent scoring differences from scenario drift. |
| Initial state, OD requests, demand volume and departure times | Compare the same dispersal task. |
| Frozen per-driver navigation policy implementation | Only joint dependence may be controlled. |
| Compliance mechanism and parameters (within a configuration) | Isolate the treatment effect. |
| Observation protocol (within a configuration) | Give methods compatible information access. |
| Simulation step, coordination decision frequency, termination and scoring window | Keep `J` comparable. |
| Predeclared seed list / external random streams | Support paired comparisons; avoid cherry-picking. |

**Do not** force later traffic states or future `p_{i,t}` to match across methods: policy-induced differences in congestion and navigation inputs are **part of the closed-loop treatment effect**. The same numeric seed alone does not ensure identical random draws if the simulation call order differs. Prefer pre-generated demand and exogenous behavioral random streams where feasible; record separate seeds for scenario, driver compliance and route sampling.

**Training versus evaluation [Proposed]:** Tune learned policy parameters and FIX/RND hyperparameters on training or validation scenarios only. Use held-out seeds and, if feasible, held-out demand patterns for final scores. Freeze hyperparameters before test evaluation. If resources are too limited for a scenario split, explicitly report that the results test only the chosen conditions rather than generalization.

## 6. Reporting and statistical analysis

**Unit of replication:** One *complete dispersal episode* for a specific method, scenario and seed. Time steps within one episode are not independent statistical replicates.

For metric `J`, pair each coordinated run with the IND run under the same scenario/seed. Define

\[
D_s^{(m)}=J_{\mathrm{IND},s}-J_{m,s}, \qquad
I_s^{(m)}=100\frac{J_{\mathrm{IND},s}-J_{m,s}}{J_{\mathrm{IND},s}}\%.
\]

- Positive `D_s` means the method improved the overload score.
- Only compute `I_s` where `J_IND,s > 0`; if `J_IND,s = 0`, mark percentage improvement undefined and report absolute difference.
- Report each method's mean/median `J_0.90` across seeds, plus uncertainty (e.g. standard deviation and 95% *paired bootstrap confidence interval* for the mean `D_s` where the number of runs permits). Report the number of seeds.
- Report `J_0.99` using the **same** trajectories; do not silently retune the algorithm against this secondary metric.
- Report E2/E3 as curves of paired improvement vs compliance / delay, with uncertainty and the common reference setting marked.
- Report extra-travel-time distributions across drivers, and explain that drivers within the same episode are statistically dependent; use episode-aware summaries/uncertainty rather than treating every driver as an independent trial.
- Include negative results and failure modes; do not claim causation beyond the controlled simulator assumptions or generalization to real-world traffic. **[Proposal §§3.3, 4.3]**

**Suggested figures [Proposed]:**
1. Main comparison: `J_0.90` by method with variability across seeds.
2. Time evolution: realized per-window overload for an illustrative *matched* episode (identify as example rather than aggregate evidence).
3. Compliance: mean paired improvement vs compliance.
4. Delay: mean paired improvement vs observation delay.
5. Fairness: ECDF, violin plot or histogram of `ΔTT_i`, plus upper-tail summary.
6. Optional: heatmap of link occupancy/overload and route allocation to visualize bottleneck shifting.

## 7. Input/output contract for integration with teammates

The evaluator should accept the following **minimum tables** or equivalent structured data. Field names are **proposed**, not required by the proposal. The exact export format can be CSV or Parquet as long as types and semantics are documented.

**`run_manifest.csv`** — one row per run:

`run_id, method, scenario_id, demand_id, seed, compliance_model, compliance_rate, delay_seconds, observed_link_set_id, sim_step_seconds, decision_interval_seconds, episode_end_seconds, policy_version, sampler_version`

**`link_occupancy.csv`** — one row per monitored link and simulator step:

`run_id, sim_time_seconds, decision_epoch, link_id, true_occupancy, overload_threshold`

**`vehicle_trips.csv`** — one row per driver and run:

`run_id, vehicle_id, origin_id, destination_id, departure_time_seconds, arrival_time_seconds, travel_time_seconds`

**`recommendation_samples.csv`** — for auditing *recommendation* marginals:

`run_id, decision_epoch, vehicle_id, sampled_full_path_id, accepted_recommendation`

**`marginal_reference.csv`** — the frozen individual policy output at each decision input:

`run_id, decision_epoch, vehicle_id, full_path_id, reference_probability`

For exact or Monte Carlo marginal checks, also request a reproducible fixed-input sampling interface from the coordination owner: `sample_joint(marginals, observation, theta, seed)`, or equivalent, that can be invoked repeatedly while holding all decision inputs constant. The main closed-loop run cannot replace this test, because its marginals evolve with traffic.

## 8. Execution order and minimal viable study

1. **Agree definitions/interfaces:** Confirm metric calculation from Task 1, decision interval, thresholds, compliance, observation lag, episode termination and files to be exported.
2. **E0 + small network:** Validate sampler constraints and correct scoring before running performance comparisons.
3. **E1 pilots:** Run 2–3 seeds to detect integration bugs; **exclude** pilot runs from formal conclusions if they were used for tuning.
4. **E1 full:** Freeze parameters, run at least the pre-agreed matched seeds and summarize `J_0.90`, `J_0.99` and extra travel time.
5. **E2 and E3:** One-factor-at-a-time robustness sweeps, reusing the E1 reference configuration instead of needlessly repeating it.
6. **Stage B robustness:** Repeat key comparisons on Monaco SUMO, or document fallback/limitations.
7. **Finalize figures/report:** Present supported improvements, uncertainty, counterexamples and fairness costs.

**Example computational budget [Proposed]:** With 4 methods, 10 seeds, 4 compliance values and 4 delay values, separate one-factor sweeps sharing one reference configuration require `4 × 10 × (4 + 4 − 1) = 280` *evaluation episodes per scenario*. A complete crossed sweep would require `4 × 10 × 4 × 4 = 640` episodes per scenario. These counts exclude training, tuning, optional partial-observation sweeps and pilots. Reduce seeds or grid size for early debugging, but keep the final comparison balanced.
